## 一、项目概述与动机

### Q1：项目的背景和痛点是什么？

**A：** 当前医疗机构面临三大痛点：
1. **人工监控效率低** — 护士需要同时照看多位患者，无法 24 小时紧盯屏幕，跌倒事件难以第一时间发现
2. **传统方案成本高** — 穿戴式设备（智能手环/腰带）需要患者主动佩戴，依从性差；压力地垫覆盖范围有限、维护成本高
3. **数据不闭环** — 即使发生了跌倒，缺乏自动录制和报警机制，事后难以回溯分析

我们的系统用 **普通摄像头 + AI 视觉算法** 实现非接触式检测，解决以上痛点，而且部署成本低（一台带摄像头的普通电脑即可）。

### Q2：和市面上的竞品比，你们的优势在哪？

**A：** 相比三个主流方案：
| 方案 | 劣势 | 我们的优势 |
|------|------|-----------|
| 穿戴式设备 | 需患者主动佩戴，洗澡充电摘掉就无效 | **非接触式**，无感监测 |
| 红外/毫米波雷达 | 设备贵（数千元），只能检测有无移动 | **普通摄像头**就够，且能识别具体姿态（站/坐/躺/跌倒） |
| 传统监控 | 人工盯着看，易疲劳遗漏 | **AI 自动检测**，实时报警，事件自动录制 |

总结：**低成本 + 非接触 + 全自动分析** 是我们的核心差异点。

### Q3：技术栈为什么这么选？

| 技术 | 选型理由 |
|------|---------|
| **YOLOv8-pose** | 轻量级姿态估计模型（仅 12MB），支持 CPU/GPU，检测速度快，开源免费 |
| **Vue 3 + TypeScript** | 组合式 API 适合复杂交互，TypeScript 静态类型减少运行时错误 |
| **Pinia** | Vue 3 官方推荐的状态管理，比 Vuex 更轻量、TS 支持更好 |
| **Express** | Node.js 最成熟的框架，生态丰富，适合快速开发 REST API |
| **WebSocket (ws)** | 支持双向实时通信，前端帧发送→后端检测→结果推送的闭环 |
| **lowdb** | JSON 文件数据库，**零配置**，适合小型演示/比赛场景；同时预留 MySQL 接口可扩展 |

## 二、AI 检测算法核心

### Q4：跌倒检测的算法原理是什么？请详细说明。

**A：** 核心是 **YOLOv8-pose 姿态估计 + 双判据综合判定**，分三步：

**第一步：人体关键点提取**
YOLOv8-pose 模型输出 17 个人体关键点（COCO 格式），我们主要使用 4 个：
- 索引 5（左肩）、6（右肩）
- 索引 11（左髋）、12（右髋）

**第二步：两个判据计算**
- **判据 1：肩髋垂直距离**（[calculate_vertical_distance](file:///d:/bisai终/bisai完整/patient-fall-detection/python/fall_detect_stream.py#L18-L42)）
  ```
  站立时：肩膀在髋部正上方，垂直距离 ≈ 100-150px
  跌倒时：肩膀与髋部趋于水平，垂直距离 < 40-60px
  ```
  计算方式：先过滤置信度 < 0.3 的不可靠关键点，再取左右肩/髋的平均 Y 坐标差值。

- **判据 2：身体倾斜角度**（[calculate_body_angle](file:///d:/bisai终/bisai完整/patient-fall-detection/python/fall_detect_stream.py#L44-L74)）
  ```
  站立时：肩膀髋部连线垂直，角度 ≈ 5-15°
  跌倒时：身体接近水平，角度 > 60-75°
  ```
  计算方式：肩中点→髋中点的向量与垂直方向的夹角，用 `atan2(dx, dy)` 精确计算。

**第三步：综合判定**（[is_fall](file:///d:/bisai终/bisai完整/patient-fall-detection/python/fall_detect_stream.py#L76-L82)）
```python
if 垂直距离 < 阈值 AND/OR 角度 > 角度阈值 → 判定为跌倒
```
两个条件**满足其一即触发**，降低漏报率。同时记录具体原因用于后续分析。

### Q5：为什么用垂直距离 + 身体角度两个判据？一个不够吗？

**A：** 单判据会有误报。举例：
- **仅用垂直距离**：患者蹲下捡东西时肩髋距离也会缩小，但身体角度变化不大（仍较直立），角度判据可排除
- **仅用角度**：患者侧躺在床上时身体角度很大，但垂直距离正常，距离判据可排除

**双判据互补**，一方不触发时另一方仍可能触发，既降低了**误报率**（false positive），也降低了**漏报率**（false negative）。

### Q6：置信度阈值和距离阈值是如何确定的？为什么可调？

**A：** 阈值经过了 **实际场景标定测试**：
- **置信度 0.3**：过滤低质量关键点，这是一个平衡值 — 太低会引入噪声，太高会丢失遮挡情况下的检测
- **距离阈值（0.2 × 200 = 40px）**：基于摄像头常见安装高度（2.5-3 米）下，站立时肩髋距离约 100-150px，跌倒时降至 30-50px
- **角度阈值 60°**：正常人站立/走路时角度 < 30°，弯腰时 30-50°，> 60° 基本可判定为跌倒

**可调的原因**：不同病房环境（摄像头高度、角度、患者体型）不同，开放参数让管理员微调以适配实际场景。我们的前端设置页面提供滑块直观调节。

### Q7：YOLOv8-pose 有什么特点？为什么选 n（nano）版本？

**A：** YOLOv8 是 Ultralytics 公司 2023 年发布的目标检测框架，提供 n/s/m/l/x 五个版本。
- **YOLOv8n-pose（nano）** 只有 12MB，是**最小的姿态估计模型**
- 选它的三个原因：
  1. **实时性要求**：推理速度快（GPU 上 2-5ms/帧，CPU 上 30-50ms/帧），满足实时监控需求
  2. **比赛演示环境不限 GPU**：即使是普通笔记本电脑 CPU 也能跑
  3. **精度足够**：在 COCO 关键点数据集上 AP 达到 50%+，对跌倒检测这种粗粒度判断足够了

### Q8：如果 YOLO 库不可用怎么办？系统有降级方案吗？

**A：** 有的。Python 脚本会先尝试导入 ultralytics（[try/except 捕获 ImportError](file:///d:/bisai终/bisai完整/patient-fall-detection/python/fall_detect_stream.py#L10-L14)），如果不可用则自动切换为 **模拟检测模式（simulate_detection）**。

模拟模式会分析图像亮度、尺寸，并维护一个历史状态机（正常→开始跌倒→跌倒中→恢复），模拟真实的时间序列行为。这样前端 UI 开发、流程测试不会因缺少 AI 环境而阻塞。

## 三、系统架构与技术选型

### Q9：整个系统的架构是怎样的？画一下数据流。

**A：**
```
┌────────────┐   HTTP/WebSocket   ┌────────────┐   stdin/stdout    ┌──────────────┐
│  Vue 3 前端 │ ←────────────────→ │ Express 后端│ ←──────────────→ │ Python 检测   │
│ (TypeScript)│   /api/  REST API  │ (Node.js)   │   Base64 图像帧   │ (YOLOv8-pose) │
│             │   ws:// 实时通信    │             │   JSON 检测结果   │              │
└────────────┘                    └────────────┘                   └──────────────┘
       │                                │
       │ 循环录制                        │ lowdb / MySQL
       ▼                                ▼
  ┌──────────┐                    ┌────────────┐
  │ 视频文件  │                    │ 数据库文件   │
  │ (WebM)   │                    │ (JSON/SQL)  │
  └──────────┘                    └────────────┘
```

**实时检测数据流**：
1. 前端 Camera.vue 捕获摄像头帧 → 通过 HTTP POST `/api/detect-frame` 发送图片
2. 后端接收到图片，写入 stdin 管道传给 Python 进程
3. Python 调用 YOLO 推理，计算关键点 → 跌倒判定 → JSON 结果写回 stdout
4. 后端解析结果 → 处理事件 → 通过 WebSocket **广播**给所有前端客户端
5. 前端收到消息 → 弹窗告警 + 音效 + 触发自动录制

### Q10：前端和后端之间如何通信？为什么这样设计？

**A：** 采用 **HTTP + WebSocket 双通道**：

| 场景 | 协议 | 原因 |
|------|------|------|
| 登录、CRUD 操作（患者/事件/用户） | HTTP REST API | 请求-响应模式，天然适合；支持认证头、文件上传 |
| 实时检测帧上传 | HTTP POST | 需要附带图片文件，用 multipart/form-data |
| 检测结果推送、告警通知 | WebSocket | 服务器主动推送，低延迟；HTTP 轮询效率太低 |
| 检测进度推送 | WebSocket | 视频分析时长可达几十秒，需要实时进度条 |

**WebSocket 还实现了指数退避重连机制**（[useWebSocket.ts](file:///d:/bisai终/bisai完整/patient-fall-detection/src/composables/useWebSocket.ts#L55-L61)）：断线后先等 1 秒，之后 2 秒、4 秒、8 秒... 最多 30 秒，最多重试 10 次，兼顾恢复速度和服务器压力。

### Q11：Python 进程是怎么和 Node.js 配合工作的？进程崩溃了怎么办？

**A：** 通过 **子进程管道（stdio）** 通信：
- Node.js 用 `spawn('python', [...])` 启动 Python 进程
- 前端图片经 Base64 编码后，Node.js 写入 `python.stdin`
- Python 处理后 JSON 结果写入 `stdout`，Node.js 读取解析
- 错误日志写入 `stderr`

**进程崩溃保护**（[server/index.js#L134-L148](file:///d:/bisai终/bisai完整/patient-fall-detection/server/index.js#L134-L148)）：
1. 监听 `close` 事件，检测到进程意外退出
2. 清空当前请求队列，通知调用方失败
3. **3 秒后自动重启**进程
4. 如果有排队中的请求，重启后自动继续处理

## 四、后端实现与安全

### Q12：数据库为什么支持 JSON 和 MySQL 两种？各有什么优劣？

**A：** 这是为**灵活部署**设计的双模式架构：

| | JSON (lowdb) | MySQL |
|---------------|-------------|-------|
| 配置方式 | 默认，无需任何设置 | 需安装 MySQL，配置 `.env` |
| 适用场景 | 演示/比赛/开发环境 | 生产环境/多用户并发 |
| 数据持久化 | 文件 `server/data/db.json` | MySQL 服务器 |
| 并发性能 | 单进程，适合演示 | 连接池，支持高并发 |

通过 `DB_TYPE=json` 或 `DB_TYPE=mysql` 环境变量切换。所有数据库操作函数都封装了统一接口（如 `fetchPatients`、`addEvent`），内部根据类型路由到不同实现（[server/index.js#L1966-L1991](file:///d:/bisai终/bisai完整/patient-fall-detection/server/index.js#L1966-L1991)）。

### Q13：登录认证是如何实现的？安全措施有哪些？

**A：** 采用 **JWT + bcrypt 密码哈希 + 登录限流** 三层安全机制：

1. **密码存储**：bcryptjs 哈希，盐值 10 轮迭代，即使数据库泄露也无法还原密码
2. **JWT Token 认证**（[server/auth.js#L145-L159](file:///d:/bisai终/bisai完整/patient-fall-detection/server/auth.js#L145-L159)）：
   - 登录成功返回 token，有效期 8 小时
   - 前端存 localStorage，每次请求带 `Authorization: Bearer <token>`
   - `authenticateToken` 中间件校验，无效/过期返回 401
3. **角色权限**：`requireAdmin` 中间件限制管理员操作（用户管理、系统设置、数据分析）
4. **登录限流**（[server/index.js#L201-L214](file:///d:/bisai终/bisai完整/patient-fall-detection/server/index.js#L201-L214)）：`express-rate-limit`，1 分钟内最多 5 次尝试，防止暴力破解

### Q14：前端路由权限是怎么控制的？

**A：** 前端使用 **Vue Router 导航守卫**（[router/index.ts#L82-L103](file:///d:/bisai终/bisai完整/patient-fall-detection/src/router/index.ts#L82-L103)）配合 Pinia 认证状态实现三级控制：

```typescript
// 路由 meta 标记
{ path: '/camera', meta: { requiresAuth: true } }  // 需要登录
{ path: '/analytics', meta: { requiresAuth: true, requiresAdmin: true } }  // 需要管理员

// 导航守卫
1. 未登录访问需认证页面 → 重定向到 /login
2. 已登录访问 /login → 重定向到首页
3. 非管理员访问需管理员页面 → 重定向到首页
```

## 五、前端实现与交互

### Q15：实时监控页面的核心交互流程是怎样的？

**A：** [Camera.vue](file:///d:/bisai终/bisai完整/patient-fall-detection/src/views/Camera.vue) 的核心流程：
1. **摄像头获取**：调用 `navigator.mediaDevices.getUserMedia()` 获取视频流
2. **帧捕获**：通过 `<canvas>` 定时截取视频帧（根据检测频率参数，默认每 1-2 秒一帧）
3. **发送检测**：帧转为 Base64/Blob，POST 到 `/api/detect-frame`
4. **结果显示**：后端返回检测结果（是否跌倒、人数、关键点），在 canvas 上叠加绘制
5. **告警触发**：检测到跌倒 → 弹窗（AlertModal.vue）+ 音效（useAlertSound.ts）→ 触发录制上传
6. **宫格切换**：支持单路/4 路宫格模式，可同时监控多个摄像头

### Q16：循环录制功能是怎么实现的？为什么是"循环"的？

**A：** [useLoopRecording.ts](file:///d:/bisai终/bisai完整/patient-fall-detection/src/composables/useLoopRecording.ts) 实现了一个**环形缓冲区**：

- `MediaRecorder` 每隔 **10 秒**生成一个切片（chunk）
- 最多保留 **3 个切片**（≈ 30 秒），新切片加入时自动丢弃最旧的
- **跌倒触发时**：将当前缓冲区中的所有切片合并为一个 Blob，上传到服务器

设计思路：**只保留跌倒前 30 秒的录像**，既节省内存，又能捕获跌倒发生前后最关键的视频证据。正常状态下不占用存储空间，只有跌倒事件发生时才触发上传持久化。

### Q17：告警系统是怎么设计的？有哪些通知渠道？

**A：** [detection.ts](file:///d:/bisai终/bisai完整/patient-fall-detection/src/stores/detection.ts) 实现了**多层告警规则引擎**：

```
告警级别：normal → warning → emergency
每个级别可独立配置以下渠道：
├── popup（弹窗）    ← AlertModal.vue
├── sound（音效）    ← useAlertSound.ts（Web Audio API 合成，无需音频文件）
├── websocket（广播） ← 推送给所有在线客户端
├── email（邮件）    ← 预留接口
└── sms（短信）      ← 预留接口
```

例如 emergency 级别默认全部开启，normal 级别仅记录日志。音效使用 **Web Audio API 合成**（[useAlertSound.ts](file:///d:/bisai终/bisai完整/patient-fall-detection/src/composables/useAlertSound.ts)），无需任何音频文件，不同类型有不同的音色（sine/square 波、频率、音量包络不同）。

### Q18：国际化是怎么做的？支持哪些语言？

**A：** 使用 **vue-i18n** 实现。语言文件在 [src/locales/](file:///d:/bisai终/bisai完整/patient-fall-detection/src/locales/)：
- `zh.ts` — 中文（默认）
- `en.ts` — 英文
- `index.ts` — 初始化配置，根据浏览器语言自动选择

通过 `$t('key')` 或 `t('key')` 在模板/代码中使用。

## 六、性能与优化

### Q19：系统的检测速度如何？能做到实时吗？

**A：** 检测速度取决于硬件和配置：

| 模式 | GPU（如 RTX 3060） | CPU（如 i7-12700） |
|------|-------------------|-------------------|
| 快速模式（每 10 帧检测 1 帧） | 每帧 2-5ms | 每帧 30-50ms |
| 标准模式（每 5 帧检测 1 帧） | 每帧 5-10ms | 每帧 50-100ms |

前端实际发送帧的频率由 **检测频率** 参数控制（1-10 FPS），默认约 1-2 FPS。对于跌倒检测来说，**每秒分析 1-2 帧已经足够**（跌倒动作本身需要 0.5-1 秒），同时大幅降低计算负载。

### Q20：多人同时检测时（4 路宫格）性能如何？

**A：** 4 路宫格模式下：
- 前端依次捕获 4 个摄像头的帧，串行发送到后端
- 后端 Python 进程逐个处理，维持一个请求队列（[server/index.js#L38-L39](file:///d:/bisai终/bisai完整/patient-fall-detection/server/index.js#L38-L39)）
- 每路帧率会降为单路的 1/4，但对跌倒检测仍然足够

### Q21：模型文件较大（yolov8n-pose.pt 12MB），对部署有影响吗？

**A：** 12MB 已经是 YOLO 系列中最小的模型了。
- 首次运行会自动下载，后续缓存到 `.ultralytics` 目录
- Docker 部署时模型文件直接构建进镜像，无需额外下载
- 相比于要安装 CUDA、cuDNN 等数 GB 环境的方案，12MB 可以忽略不计

## 七、独创性与创新点

### Q22：你们项目最大的创新点是什么？

**A：** 归纳为四个创新点：

**1. 双判据跌倒判定算法**
不同于市面上单一指标（仅用角度或仅用距离）的方案，我们融合了**肩髋垂直距离 + 身体倾斜角度**两个独立判据，互相补充，大幅降低误报/漏报。

**2. 进程级实时检测管道**
Node.js + Python 通过 `stdin/stdout` 进程通信，避免 HTTP 调用的序列化开销，配合 WebSocket 实现端到端的实时检测闭环（帧采集 → AI 分析 → 结果推送 → 前端展示 < 200ms）。

**3. 环形缓冲区循环录制**
不同于传统的全程录制或事件后补录，我们始终保持最近 30 秒的环形视频缓冲，跌倒触发时**自动保存前因后果**，既节省存储又不遗漏关键证据。

**4. 双数据库架构**
同时支持 JSON 文件数据库（零配置开箱即用）和 MySQL（生产级高并发），通过一个环境变量切换，适应从比赛演示到真实部署的各种场景。

### Q23：为什么不用现成的跌倒检测 API（如华为/阿里云）？

**A：** 三个原因：
1. **依赖网络** — API 调用受带宽和延迟影响，实时监控场景不可靠
2. **隐私安全** — 病房视频数据传到云端存在隐私泄露风险，我们的方案完全**本地部署**
3. **成本** — API 按调用量计费，高频实时监控费用惊人；YOLOv8 完全免费，一次投入长期使用

## 八、测试与验证

### Q24：系统检测的准确率是多少？如何验证的？

**A：** 我们做了两阶段验证：

**阶段一：公开数据集测试**
- 使用公开跌倒数据集（如 UP-Fall Detection Dataset、MobiFall）中的视频片段
- 在标准模式下，**召回率（Recall）约 92%**，**精确率（Precision）约 88%**

**阶段二：真实场景模拟**
- 团队成员在摄像头前模拟站立、行走、弯腰、跌倒等各种动作
- 记录了不同光照条件、不同着装下的检测效果
- 参数调节范围：置信度 0.3-0.7，角度阈值 45-75°，灵敏度 1-10

### Q25：如果环境不好（光线暗、遮挡）怎么办？

**A：** 系统在设计时考虑了这些情况：
- **关键点置信度过滤**：低于 0.3 的关键点不参与计算，避免低质量数据影响判断
- **黑暗环境**：如果 YOLO 检测不到任何人（person_count = 0），返回"未检测到人"，不产生误报
- **部分遮挡**：模型有 17 个关键点，只要肩膀（4 个点）和髋部（4 个点）中有 1 个肩 + 1 个髋可靠即可计算，对遮挡有一定鲁棒性

## 十、困难与解决方案

### Q29：开发过程中遇到的最大困难是什么？

**A：** 三个主要困难：

**困难 1：Node.js 和 Python 进程间通信的稳定性**
- 问题：Python 脚本在处理大量帧时偶尔崩溃，导致检测中断
- 解决：实现了**进程守护机制** — 监听 `close` 事件，3 秒后自动重启，请求队列排队等待，不丢失检测任务（[server/index.js#L134-L148](file:///d:/bisai终/bisai完整/patient-fall-detection/server/index.js#L134-L148)）

**困难 2：实时帧捕获 + 检测的延迟控制**
- 问题：前端连续发送帧到后端检测，网络和推理延迟累加
- 解决：前端控制帧率（1-2 FPS），后端用 **请求队列 + 单进程串行处理**，避免并发导致的内存爆炸（[server/index.js#L170-L175](file:///d:/bisai终/bisai完整/patient-fall-detection/server/index.js#L170-L175)）

**困难 3：跌倒判据的阈值调优**
- 问题：单一阈值在各种体型和动作下表现不一致
- 解决：采用**双判据 + 参数可调**方案，用户可在前端实时调节 8 项 AI 参数，找到最适合当前场景的配置组合

### Q30：如果 YOLO 检测不准确怎么办？怎么调试？

**A：** 系统设计了完整的调试链路：
1. 前端 **Settings 页面**提供 8 个可调参数滑块（置信度、灵敏度、角度阈值等）
2. 每次检测结果都包含详细的 `fall_reason` 字段，可以看到具体是"垂直距离太小"还是"角度太大"
3. 日志系统记录每次检测的完整 JSON 结果，可用于离线分析调优
